# 검수 체크리스트

## A. 계약 (FE ↔ BE) — 하나라도 어긋나면 [막힘]
- 경로·메서드 일치 (`/api/v1/...`, 대소문자, 후행 슬래시)
- 요청 필드: 이름·타입·필수 여부. FE가 보내는데 BE 스키마에 없는 필드 / BE 필수인데 FE가 안 보내는 필드
- 응답 필드: FE가 읽는 필드가 BE 응답에 존재하고 타입이 같은가 (특히 날짜 문자열, null 허용)
- 상태 코드: FE가 기대하는 성공 코드(200/201/202)와 BE가 내는 코드
- 오류 코드: FE가 분기하는 `code`가 BE `error-codes`에 정의되어 있는가
- 페이지네이션: 커서 필드 이름 일치

## B. 기획 대비 — [기능 오류]
- spec의 모든 UC 주 흐름이 Endpoint + 화면으로 구현되었는가
- 예외 흐름(E1, E2 …)마다 오류 응답과 화면 처리가 있는가
- 범위 밖(spec §2 Out)이 구현되지 않았는가
- 비기능 요구(권한, 멱등성)가 반영되었는가

## C. 설계 대비 (FE) — [경고]
- components.json의 screen·component가 모두 존재하는가
- 네 상태(기본·로딩·빈·오류) 처리
- 카피가 설계서 §4와 같은가
- 토큰 외 임의 값 사용

## D. 규약 (BE) — [경고]
- 엔티티가 응답으로 노출되지 않는가
- Controller에 트랜잭션·try/catch 없음
- 마이그레이션이 파괴적이지 않은가
- 새 오류 코드가 error-codes.md에 등록되었는가

## E. 보안 — 발견 시 [막힘]
- 본인 리소스 검사 누락 (다른 사용자 id로 접근 가능한가)
- 시크릿·토큰 하드코딩, 로그 노출
- 클라이언트에 서버 전용 env 노출

## F. 테스트
- 결과물 요약의 테스트 결과가 통과인가
- 새 Endpoint마다 통합 테스트, 새 컴포넌트마다 렌더 테스트 존재
