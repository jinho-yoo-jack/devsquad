# Go 포팅 — 결정, 계약, 전환, 검증

기록일: 2026-10-06. 범위는 Java Control Plane과 Python Agent Runtime을 Go로 전환하는 작업이다. Next.js 웹과 사용자 저장소의 `.devsquad/` 형식은 유지한다.

## 프레임워크 조사와 결정

| 후보 | 공식 자료에서 확인한 기능 | 이번 프로젝트 판단 |
|---|---|---|
| Go `net/http` | Go 1.22부터 메서드·경로 변수 라우팅 지원 | **HTTP 계층에 채택**. 현재 REST 라우트는 표준 라이브러리로 충분하다. |
| Gin | 라우터·미들웨어·요청 처리 프레임워크 | 편의 기능은 있지만 현재 규모에서 별도 HTTP 프레임워크를 추가할 필요가 작다. |
| Eino | 그래프 중단·재개, CheckPointStore 인터페이스 | LangGraph와 가까운 후보. 체크포인트 저장소는 직접 구현해야 하며 실행 복구 운영 설계도 필요하다. |
| Temporal Go SDK | 실행 이력, Worker 복구, Query·Signal·Update, Activity 재시도 | **Agent Runtime에 채택**. 장시간 사람 승인 대기와 프로세스 재시작 복구를 주요 선택 기준으로 삼았다. 별도 Temporal 서비스 운영 비용을 수용한다. |

위 판단은 프로젝트 요구와 공식 기능을 비교한 설계 결정이며 성능 벤치마크 결과가 아니다.

출처: [Go 라우팅](https://go.dev/blog/routing-enhancements), [Gin 소개](https://gin-gonic.com/en/docs/introduction/), [Eino 체크포인트](https://www.cloudwego.io/docs/eino/core_modules/chain_and_graph_orchestration/checkpoint_interrupt/), [Temporal 메시지·Update](https://docs.temporal.io/develop/go/workflows/message-passing), [Temporal 테스트](https://docs.temporal.io/develop/go/best-practices/testing-suite).

PostgreSQL은 [pgx](https://github.com/jackc/pgx), Redis는 [go-redis](https://github.com/redis/go-redis)를 사용한다. 의존성 버전은 루트 `go.mod`와 `go.sum`에 고정한다. 실제 모델 연동은 [Anthropic Messages](https://platform.claude.com/docs/en/api/messages/create), [OpenAI Chat Completions](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)의 도구 호출 형식을 사용한다.

## 구현 구조

- `control-plane/cmd/control-plane`: 설정, DB 이관, Redis consumer, 복구 작업, HTTP 서버
- `control-plane/internal/controlplane`: Controller → FacadeService → Service → Repository. Facade가 트랜잭션과 응답 조립을 소유한다.
- `agent-runtime/cmd/agent-runtime`: HTTP 서버와 Temporal Worker
- `agent-runtime/internal/runtime`: 파이프라인 검증, 정의 로딩, 작업 디렉토리, 파일 도구, 모델 어댑터, Activity, 워크플로

Task 생성은 queued 저장 → Runtime 호출 → Stage 저장 순서다. Runtime 장애 시 queued를 복구 작업이 재전송한다. 승인 결정은 Task 행 잠금 아래 승인·Stage·Task를 함께 커밋한 뒤 Runtime에 전달하며, 실패 시 resume_pending을 재시도한다. 병렬 Stage 중 아직 대기 중인 승인이 있으면 Task는 waiting_approval을 유지한다.

Redis의 seq 발급·XADD·발행 중복 검사는 Lua로 원자 처리한다. Consumer는 성공한 이벤트만 ACK하고 오래된 pending 이벤트를 XAUTOCLAIM으로 회수한다. Stage 인벤토리보다 먼저 도착한 이벤트는 재시도한다. 잘못된 envelope는 dead-letter로 보낸다. approval_id를 보강한 envelope를 DB에 저장해 REST와 WebSocket 재생이 같은 내용을 반환한다.

Temporal 워크플로는 승인된 모든 의존 Stage가 끝난 뒤 후속 Stage를 시작한다. LLM·파일·Redis는 Activity에서만 호출한다. 승인에는 검증과 완료 응답을 제공하는 **Update**를 사용하고, approval_id를 Update ID로 사용한다. 동일 Update 재전송은 재실행하지 않는다. 기존 LangGraph의 checkpoint_id 응답 필드는 Temporal Run ID를 반환하도록 의미를 변경했다.

## API 호환성과 변경

다음 기존 경로와 snake_case 응답을 유지한다.

- `/api/v1/projects`, `/api/v1/projects/{id}`
- `/api/v1/tasks`, `/api/v1/tasks/{id}`, `/{id}/pause|resume|cancel`
- `/api/v1/approvals`, `/api/v1/approvals/{id}`, `/{id}/decide`
- `/api/v1/tasks/{taskId}/approvals`, `/{taskId}/events?after_seq=&limit=`
- `/api/v1/health`, `/actuator/health`, `/ws`
- Runtime `/health`, `/runs`, `/runs/{task_id}/resume|continue|cancel|state`

`project_id`·`after_seq`를 정식 query parameter로 처리하며 기존 Java식 projectId·afterSeq도 받는다. 상태 필터는 대소문자 모두 받는다. 빈 컬렉션은 배열로 반환한다. 현재 Task 목록은 기존처럼 next_cursor=null이며 cursor pagination은 아직 구현하지 않았다.

Runtime `/runs/{task_id}/pause`를 추가했다. pause는 현재 실행 중 Activity가 끝난 뒤 다음 단계 진입을 막는다. `/continue`는 pause 해제 또는 반려 상한으로 막힌 Stage의 수동 재개를 수행한다. 승인 결정 본문은 다음과 같이 확장했다. 공개 승인 API 요청에는 새 필드를 넣을 필요가 없으며 CP가 DB 정보로 채운다.

```json
{
  "approval_id": "uuid",
  "stage_key": "backend",
  "kind": "plan",
  "retry_no": 0,
  "decision": "approve",
  "feedback": null,
  "edited_content": null
}
```

단일 게이트만 대기 중이면 Stage 정보 없는 내부 요청도 해석할 수 있다. 병렬 게이트에서는 대상 정보가 필수다. `edit`은 계획/승인 결과 내용과 후속 Stage 입력에 반영하며, 기존 구현과 마찬가지로 이미 생성된 원본 파일의 본문을 직접 수정하지 않는다.

Spring의 자동 Swagger, Actuator metrics/info 및 FastAPI `/docs` 자동 생성은 제거했다. 공개 API는 기존 Phase 1처럼 로컬 단일 사용자용이며 JWT·Discord·GitHub 실제 연동은 이번 포팅에서 새로 구현하지 않았다. Redis 없는 JSONL 모드와 메모리 체크포인트 모드는 제거했으며, Fake LLM 실행도 Redis·Temporal을 사용한다.

## 기존 설치 전환

1. **기존 버전에서 진행 중 Task를 완료하거나 취소한다.** LangGraph 체크포인트는 Temporal 실행 이력과 호환되지 않는다. 기존 workspace와 langgraph 스키마는 삭제하지 않는다.
2. PostgreSQL과 workspace를 백업하고 기존 Java/Python 프로세스를 중지한다. 구버전과 신버전을 같은 업무 DB에 동시에 연결하지 않는다.
3. 새 Temporal 서비스를 준비한다. 개발 Compose는 SQLite 파일을 named volume에 보관한다. [공식 CLI 문서](https://github.com/temporalio/documentation/blob/main/docs/cli/setup-cli.mdx)의 start-dev는 개발용이며 운영에서는 Temporal Cloud 또는 운영용 클러스터를 사용한다.
4. Go Control Plane을 시작한다. 기존 7개 업무 테이블을 인계하고, JPA 대문자 status/kind를 소문자로 정규화한다. 기존 대문자 상태의 미완료 Task가 있으면 이관을 거부한다. Flyway 이력은 유지하며 Go 이관 버전은 devsquad_schema_version에 기록한다.
5. `DEVSQUAD_DB_URL`, `DEVSQUAD_REDIS_URL`, Temporal 주소, 내부 토큰, workspace 경로를 설정해 Go Runtime과 웹을 시작한다. Spring 설정 변수와 Python DEVSQUAD_FORCE_DB/USE_REDIS는 새 서버에서 사용하지 않는다.
6. 새 Task로 승인 흐름을 확인한다. 구버전으로 되돌릴 경우 enum 정규화 전 DB 백업과 구버전 코드·checkpoint를 함께 사용한다.

Temporal 이력, Redis 데이터, Runtime workspace 세 저장소를 모두 보존해야 한다. 기본 배포는 CP·Runtime 각각 한 인스턴스다. CP의 실시간 WebSocket 전송은 프로세스 내 구독자 대상이며 여러 CP 인스턴스 간 전송은 후속 작업이다.

## 검증과 한계

재현 명령은 `make test build`, `make test-integration`이다. 통합 테스트는 별도 DB schema·Redis stream·Temporal task queue를 사용한다.

2026-10-06 실제 실행 결과: Go race 테스트와 `go vet` 통과, PostgreSQL 통합 테스트 통과, Runtime 재시작·완료 후 승인 재전송을 포함한 서버 통합 테스트 통과, 두 Go 서비스 Docker 이미지 빌드 통과, 웹 TypeScript 검사·26개 테스트·Next.js production build 통과. 유료 모델 대신 Fake LLM과 공급자 HTTP mock을 사용했다.

- Go 단위·워크플로 테스트: 상태 전이, 승인 유효성, DAG·예제 정의, 파일 접근 제한, 공급자 도구 호출 형식, 병렬 승인·join·edit·반려·수동 재개
- PostgreSQL 통합: Java baseline 인계, enum 정규화, queued 복구, 승인 동시 클릭의 단일 성공, resume_pending 복구, 이벤트 중복 방지와 재생 payload
- 서버 통합: 실제 Go CP/Runtime, PostgreSQL·Redis·Temporal, 병렬 게이트, 반려, 승인 대기 중 Runtime 프로세스 재시작, 결과 파일, REST/WS 재생 일치

실제 유료 LLM 호출과 운영 Temporal 배포는 검증 범위에 포함하지 않는다. LLM·파일 작업 Activity는 장애 시 재시도될 수 있다. 완료한 Activity 결과는 workspace 캐시에 저장하지만 실행 도중 장애에서는 도구 부작용이 반복될 수 있으므로 exactly-once 실행을 보장하지 않는다. run_tests는 신뢰하는 저장소 설정 명령이며 OS 샌드박스는 아니다. 기존 미구현이었던 GitHub PR 발행과 토큰 예산 강제는 계속 후속 범위다.

웹 잠금 파일은 변경하지 않았다. 테스트 환경 복구를 위한 `npm ci`에서 기존 의존성에 대한 audit 결과 9건(moderate 4, high 3, critical 2)이 보고되었으며, 웹 의존성 업그레이드는 이번 언어 포팅 범위에 포함하지 않았다.
