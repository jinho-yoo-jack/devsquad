## 1. 결정 요약

| # | 결정 | 근거 |
|---|---|---|
| D1 | Control Plane과 Agent Runtime을 **Go 단일 서비스**(`devsquad`)로 합친다 | 두 서비스로 나눈 이유는 두 가지였다. 하나는 LangGraph가 Python 런타임에서만 의미가 있다는 것, 다른 하나는 LLM 지연이 Discord 3초 응답 제한과 충돌한다는 것이다(README "왜 Spring Boot + Python 두 서비스인가?"). Go 하나로 옮기고 실행을 goroutine으로 분리하면 두 이유가 모두 사라진다 |
| D2 | 그래프 실행은 라이브러리 없이 **직접 구현한다**. DB의 Task·Stage·Approval 행이 곧 체크포인트다 | 쓰는 LangGraph 기능은 DAG 병렬, 결과 병합, 승인 대기·재개, 체크포인트뿐이다. 현행 CP에 이미 상태 기계가 있어서 프레임워크 체크포인트를 들이면 상태를 두 곳에 저장하게 된다. 후보 비교는 §13 |
| D3 | LLM은 **자체 `LLM` 인터페이스 + 공식 SDK 어댑터**로 한다(Anthropic, OpenAI, Ollama는 OpenAI 호환) | LangChain에서 쓰던 기능은 공급자 선택과 메시지·도구 형식 변환뿐이다. 공식 SDK를 쓰면 캐싱 같은 공급자별 기능을 잃지 않는다 |
| D4 | 서비스 사이 통신(내부 HTTP `/runs/*`, `X-Internal-Token`, Redis Stream, consumer group, dead-letter)을 **제거한다** | 한 프로세스 안의 함수 호출과 DB 트랜잭션으로 바뀐다 |
| D5 | Stage 실행 순서는 **선행 Stage가 모두 승인되면 즉시 시작**하는 방식으로 한다 | 같은 레벨 전체를 기다리는 BSP보다 빠르고, 의존 관계는 똑같이 지킨다. UI용 `levels`는 계속 계산해서 내려준다 |
| D6 | **외부 계약을 유지한다.** REST(`/api/v1/*`), WebSocket(`/ws`) 프로토콜, 이벤트 envelope과 type, `.devsquad/` 형식을 바꾸지 않는다 | `web/`을 수정하지 않기 위해서다 |
| D7 | 1차 목표는 **단일 인스턴스**다. 여러 인스턴스로 늘릴 자리(lease 컬럼, 브로드캐스트 인터페이스)만 만들어 둔다 | 여러 인스턴스를 지원할지는 아직 정하지 않았다(§15) |

## 3. 아키텍처

### 3.1 전후 비교

```
[현행]
 Web/Discord ─HTTP/WS─► Control Plane(Spring) ──HTTP /runs/*──► Agent Runtime(FastAPI)
                          ▲  │ Postgres(public)                    │ LangGraph + PostgresSaver(langgraph 스키마)
                          │  └──────────────◄── Redis Stream ◄─────┘ (XADD envelope, INCR seq)
                          └ EventDispatcher(XREADGROUP → 저장 → 상태 전이 → WS)

[목표]
 Web/Discord ─HTTP/WS─► devsquad (Go, 단일 프로세스)
                          ├ httpapi / ws ─► app(Task·Approval·Project 서비스, 트랜잭션 경계)
                          │                    │ commit 후 ─► orchestrator.Reconcile(taskID)
                          ├ orchestrator ──► stage runner(goroutine) ─► llm / tools / workspace
                          │      └ 상태 변경 + 이벤트 기록 = 같은 트랜잭션
                          ├ eventbus(프로세스 내부) ─► ws hub, notifier(Discord 자리)
                          └ Postgres(public 스키마 하나, langgraph 스키마 폐기)
```

### 3.2 핵심 아이디어: 레벨 트리거 Reconcile

실행 상태는 메모리가 아니라 DB의 Stage 상태다. Orchestrator가 하는 일은 하나다.

> **`Reconcile(taskID)`**: DB의 Task·Stage 상태를 읽는다. "지금 진행할 수 있는데 아직 실행 중이 아닌" Stage마다 goroutine을 하나씩 띄운다.

현행의 여러 실행 경로가 모두 이 함수 하나로 모인다.

| 현행 | 목표 |
|---|---|
| `POST /runs`(시작) | Task 생성 트랜잭션 커밋 → `Reconcile` |
| `POST /runs/{id}/resume` + `Command(resume=…)` | 승인 결정 트랜잭션 커밋(Stage 상태 전이 포함) → `Reconcile` |
| `POST /runs/{id}/continue`(재시작 복구) | 기동할 때와 주기적으로 터미널이 아닌 Task 전체에 `Reconcile` |
| `resume_pending` + RunRecoveryJob 재전송 | 필요 없어진다. 결정이 커밋되면 상태가 이미 DB에 있으니, 다음 `Reconcile`이 알아서 이어간다 |
| `GET /runs/{id}/state`, stranded 판정 | DB 조회로 대체 |

## 4. 패키지 구조

```
cmd/devsquad/main.go            # 설정 로드, 마이그레이션, 의존성 조립, 서버/복구 루프 기동, graceful shutdown
internal/
  config/        # caarlos0/env 구조체 (DEVSQUAD_* 접두사 유지)
  httpapi/       # huma 핸들러. 요청 검증, DTO 변환, 오류 코드 매핑. 비즈니스 로직 없음
  ws/            # /ws 핸들러, 세션 레지스트리, Task별 구독, 재생
  app/           # 유스케이스 서비스: TaskService, ApprovalService, ProjectService. **트랜잭션 경계가 있는 유일한 계층**
  domain/        # Task/Stage/Approval 상태 기계(순수 함수), 값 타입, 도메인 오류
  orchestrator/  # Reconcile, 실행 중 레지스트리, 취소, 복구 루프
  stage/         # Stage 단계 실행기: plan, execute(ReAct). 노드 본문의 Go 이식
  pipeline/      # pipeline.yaml 파싱·검증·위상 정렬(levels)·terminal
  agentdef/      # .devsquad/agents/* 로더, 프롬프트 빌더(build_system/build_user 이식)
  llm/           # LLM 인터페이스, registry("provider/model"), anthropic/, openai/, fake/
  tools/         # 도구 레지스트리(tool_profile → 도구), Sandbox, run_tests
  workspace/     # Task별 작업 디렉토리 준비, git 기준점, 쓰기 경로 롤백
  event/         # Emitter(트랜잭션 안 기록) + Bus(커밋 후 프로세스 내부 전송)
  store/         # sqlc 생성 코드 + WithTx 헬퍼 + 낙관적 락 헬퍼
  store/migrations/  # goose SQL (embed.FS)
```

**계층 규칙** (DSRV 4계층 규칙을 Go로 옮긴 것)
- `httpapi` → `app` → (`domain`, `store`, `orchestrator`) 방향으로만 의존한다. 핸들러 하나는 `app` 서비스 하나만 호출한다.
- 트랜잭션(`store.WithTx`)은 `app`과 `orchestrator`의 커밋 함수(§6.4)에서만 연다. `app` 서비스끼리는 서로 호출하지 않는다.
- `domain`은 DB와 트랜잭션을 모른다(현행 `TaskStateMachine`의 "순수 함수" 원칙을 유지).
- 외부 I/O(LLM, 서브프로세스, 파일 쓰기)는 트랜잭션 밖에서만 한다(§10).

## 5. 데이터 모델

### 5.1 유지
현행 `V1__baseline.sql`의 테이블 `project`, `task`, `stage`, `approval`, `deliverable`, `task_event`, `usage_record`는 그대로 쓴다. 파일은 goose 형식(`00001_baseline.sql` + `-- +goose Up`)으로 바꾼다.

### 5.2 추가 (`00002_orchestrator.sql`)

LangGraph 체크포인트(`StageState`)가 들고 있던 값을 `stage` 행으로 옮긴다.

```sql
alter table task
  add column pipeline     jsonb,                      -- 생성 시점 pipeline.yaml 스냅샷(정규화된 JSON)
  add column workspace    text,                       -- 작업 디렉토리 절대 경로
  add column event_seq    bigint not null default 0;  -- Task별 seq 발급기 (Redis INCR 대체)

alter table stage
  add column plan                  text,
  add column plan_retry_no         integer not null default 0,
  add column deliverable_ref       text,
  add column deliverable_summary   text,
  add column deliverable_retry_no  integer not null default 0,
  add column last_feedback         text,
  add column blocked_reason        text,
  add column attempt               integer not null default 0,  -- 단계 실행 시도 번호 (펜싱 토큰)
  add column lease_owner           text,                        -- 여러 인스턴스용 자리 (D7). 1차에서는 미사용
  add column lease_until           timestamptz,
  add column version               integer not null default 0;

-- 불변식은 DB 제약으로 강제한다
alter table task  add constraint ck_task_status  check (status in ('queued','running','waiting_approval','paused','blocked','completed','failed','cancelled'));
alter table stage add constraint ck_stage_status check (status in ('pending','planning','plan_review','executing','deliverable_review','approved','blocked'));
create unique index ux_approval_stage_pending on approval(stage_id) where status = 'pending';   -- Stage당 대기 승인은 1건
create unique index ux_approval_stage_kind_retry on approval(stage_id, kind, retry_no);        -- 같은 단계를 다시 실행해도 승인이 중복 생성되지 않음
```

- `approval.resume_pending`은 더 이상 쓰지 않는다. 안정화한 뒤 `00003`에서 삭제한다.
- `stage.retry_count`(현행)는 `plan_retry_no + deliverable_retry_no`로 계속 갱신한다. API 응답 호환을 위해서다.
- `langgraph` 스키마와 `infra/init.sql`의 해당 생성문은 폐기한다.

### 5.3 기존 DB
goose는 `flyway_schema_history`를 이어받지 못한다. 현재 Phase 0~1이라 운영 DB가 없다고 보고, **개발 DB는 초기화**하는 것으로 정한다(`resetdb`). 운영 DB가 이미 있다면 baseline 마킹 절차가 따로 필요하다(§15).

## 6. Orchestrator와 Stage 실행

### 6.1 Stage 상태 기계 (현행 `StageStateMachine` 확장)

```
pending ──(선행 Stage 전부 approved)──► planning
planning ──plan 완료, plan 게이트 있음──► plan_review          [approval(plan, retry_no) 생성]
planning ──plan 완료, plan 게이트 없음──► executing
plan_review ──approve|edit──► executing                        [edit: plan ← edited_content]
plan_review ──reject, retry+1 < max──► planning                [plan_retry_no++, last_feedback]
plan_review ──reject, retry+1 ≥ max──► blocked
executing ──execute 완료, deliverable 게이트 있음──► deliverable_review   [approval(deliverable) + deliverable 생성]
executing ──execute 완료, deliverable 게이트 없음──► approved             [commit_result]
deliverable_review ──approve|edit──► approved                  [edit: deliverable_summary ← edited_content]
deliverable_review ──reject, retry+1 < max──► executing        [deliverable_retry_no++, last_feedback]
deliverable_review ──reject, retry+1 ≥ max──► blocked
```

- 상태와 전이 이벤트 이름은 현행 `StageStateMachine`과 같다. `pending → planning` 전이를 일으키는 주체만 AR 이벤트(`stage.started`)에서 Orchestrator로 바뀐다.
- 반려 상한 판정(`retry_no + 1 >= max_retries`)은 현행 `stage_subgraph.make_gate`와 같은 식을 쓴다. 단, 판정 위치가 gate 노드에서 `ApprovalService.Decide` 트랜잭션 안(§10 U2)으로 옮겨진다.

**실행 가능한 상태:** `planning`, `executing`, 그리고 선행 Stage가 모두 `approved`인 `pending`. 나머지는 사람의 결정을 기다리거나(`*_review`) 끝난 상태(`approved`, `blocked`)다.

### 6.2 Reconcile

```go
// 의사 코드
func (o *Orchestrator) Reconcile(ctx context.Context, taskID uuid.UUID) error {
    t, stages := o.store.LoadTask(ctx, taskID)
    if t.Status.IsTerminal() || t.Status == Paused || t.Status == Blocked { return nil }
    if t.Status == Queued { o.commitTaskRun(ctx, t) }            // queued → running + run.started
    for _, s := range stages {
        if o.running.Has(s.ID) { continue }                      // 같은 프로세스에서 이미 실행 중
        switch {
        case s.Status == Pending && allApproved(s.DependsOn, stages):
            o.launch(t, s, StepPlan)                              // planning 전이는 claim 트랜잭션에서
        case s.Status == Planning:   o.launch(t, s, StepPlan)
        case s.Status == Executing:  o.launch(t, s, StepExecute)
        }
    }
    o.deriveTaskStatus(ctx, taskID)                               // §6.5
    return nil
}
```

- `o.running`은 `map[stageID]context.CancelFunc`이고 mutex로 보호한다. Task별 부모 context를 두고, 그 아래 Stage별 자식 context를 둔다.
- 같은 Task에 대한 `Reconcile` 호출이 겹치면 Task 단위 mutex로 직렬화한다.

### 6.3 단계 실행 (goroutine 하나 = 단계 하나)

```
launch(t, s, step):
  1. claim 트랜잭션: UPDATE stage SET status=<planning|executing>, attempt=attempt+1
                     WHERE id=$1 AND status IN (<허용 상태>) AND attempt=$2 RETURNING attempt
                     → 0행이면 다른 경로가 먼저 가져간 것이므로 종료 (펜싱)
                     + stage.started 이벤트(최초 진입일 때만)
  2. 트랜잭션 밖: LLM / 도구 / 파일 쓰기 (ctx 취소를 따름)
       - 진행 이벤트(agent.thinking, tool_call, tool_result, usage)는 Emitter로 짧은 트랜잭션에 하나씩 기록
  3. 결과 커밋 트랜잭션(§6.4): attempt가 일치할 때만 상태 전이와 결과 저장
  4. 커밋 후: running에서 제거 → Reconcile(taskID) (다음 Stage나 Task 상태 갱신)
```

- **plan 단계**: 현행 `plan` 노드와 같다. 도구 없이 LLM을 한 번 호출하고 `usage` 이벤트를 남긴다.
- **execute 단계**: 현행 `execute` + `run_react`와 같다. `max_iterations`, 결과물 헤더 삽입(`> Task: … · 버전: vN`), 요약 400자, `deliverable.produced` payload 형식을 유지한다.
- **반려 피드백 반영**: `stage.last_feedback`을 프롬프트의 `[[FEEDBACK]]`에 넣는다(현행 `build_user`와 같음).
- **선행 Stage 산출물 입력**: 선행 Stage의 `deliverable_ref`와 `deliverable_summary`로 `<inputs>`를 만든다(현행 `_prior_inputs`와 같음).

### 6.4 결과 커밋 함수

| 함수 | 같은 트랜잭션에서 하는 일 |
|---|---|
| `commitPlan` | stage.plan 저장 · 상태 전이(`plan_review` 또는 `executing`) · (게이트가 있으면) approval INSERT · `approval.requested` 이벤트 · Task 상태 갱신 |
| `commitExecute` | deliverable INSERT · stage.deliverable_ref/summary 저장 · `deliverable.produced` 이벤트 · (게이트가 있으면) approval INSERT + `approval.requested` / (없으면) `approved` + `stage.completed` · Task 상태 갱신 |

모든 커밋 함수는 `WHERE id=$1 AND attempt=$2 AND status=$3` 조건부 UPDATE로 시작한다. 0행이면 롤백하고 결과를 버린다. 취소되었거나 다른 시도가 이미 처리한 경우다.

### 6.5 Task 상태 도출

Task 상태는 현행 `TaskStateMachine`의 이벤트로만 바꾼다. 어떤 이벤트를 적용할지는 Stage 상태를 모아서 정한다.

| Stage 상태 집합 | Task 이벤트 |
|---|---|
| `*_review`가 하나 이상 | `APPROVAL_REQUESTED`(running → waiting_approval) |
| `*_review`가 없고 실행 가능한 Stage가 있음 | `APPROVED`(waiting_approval → running) |
| 전부 `approved` | `COMPLETE` + `run.completed` |
| `blocked`가 있고 실행 가능·대기 중인 Stage가 없음 | `REJECTED_OVER_LIMIT`(→ blocked) |

이렇게 하면 "병렬 Stage 중 하나라도 승인 대기면 waiting_approval"이 보장된다. 현행 EventDispatcher는 이벤트가 들어온 순서에 따라 상태가 정해져서, 다른 Stage가 승인되는 순간 waiting_approval에서 running으로 바뀔 수 있었다. 그 판정을 집합 기반으로 바꾼 것이다.

### 6.6 일시정지, 재개, 취소

- **pause**: Task `paused` 커밋. 실행 중인 단계는 끝까지 돌지만, Reconcile이 새 단계를 띄우지 않는다. 현행 의미와 같다.
- **resume**: `paused → running`(blocked이면 `MANUAL_RESUME`) 커밋 후 Reconcile.
- **cancel**: Task `cancelled` + `run.cancelled` 커밋 후 Task context를 취소한다. LLM 호출과 서브프로세스는 ctx로 중단된다. 결과 커밋은 `task.status <> 'cancelled'` 조건 때문에 0행이 되어 버려진다.

### 6.7 실패 정책

- LLM 일시 오류(429, 5xx, 네트워크)는 `llm` 계층에서 지수 백오프로 최대 3회 재시도한다.
- 그 밖의 단계 오류는 Task를 `failed`로 만들고 `run.failed{error, node}`를 남긴 뒤 형제 Stage를 취소한다. 현행에서도 그래프 예외가 나면 `run.failed`로 Task 전체가 `failed`가 되었으므로 동작이 같다.
- Stage 상태는 실패 직전 그대로 남는다. 나중에 "failed에서 재시도" 기능을 붙일 수 있다(§15).

### 6.8 재시작 복구와 단계 재실행 (멱등성)

- **기동 시**: 이전 프로세스의 goroutine은 사라졌으므로 `planning`·`executing` 상태는 모두 "중단된 단계"로 본다. 터미널이 아닌 Task 전체에 `Reconcile`을 돌리면 attempt가 오른 채로 다시 실행된다.
- **주기 실행**: `time.Timer` fixed-delay(기본 5분, `DEVSQUAD_RECOVERY_INTERVAL`)로 같은 일을 한다. 현행 RunRecoveryJob의 세 역할(queued 재시작, stranded 이어가기, resume 재전송)이 이 한 가지로 모인다.
- **plan 재실행**: 부작용이 LLM 비용뿐이라 그대로 다시 한다.
- **execute 재실행**: 파일 쓰기가 반복될 수 있다. 처리 방법은 다음과 같다.
  - workspace를 준비할 때 `git init` 후 기준 커밋을 만든다(Phase 2에서 clone으로 바꿔도 같은 방식).
  - execute를 시작할 때마다 **그 Stage의 `write_paths`만** 기준 커밋(또는 직전 승인 커밋) 상태로 되돌린다(`git checkout <base> -- <paths>` + 그 경로의 untracked 파일 정리).
  - 병렬 Stage끼리는 `write_paths`가 겹치지 않는다(현행 loader의 `_check_write_conflicts`와 같은 검증). 그래서 한 Stage를 되돌려도 다른 Stage에 영향이 없다.
  - deliverable이 승인되면 그 Stage의 경로를 커밋해서 다음 기준점으로 삼는다. 이 커밋은 workspace 안에서만 하고 push하지 않는다.

## 7. 이벤트

### 7.1 envelope과 type
현행 envelope(`event_id, task_id, seq, ts, stage_key, agent, type, payload`)과 15-API §3의 type 목록을 그대로 유지한다.

AR 원본을 CP가 재발행하던 이벤트(`approval.requested`에 `approval_id` 부여, `deliverable.produced`에 `deliverable_id` 부여)는 이제 커밋 함수가 처음부터 id를 넣어 한 번만 기록한다. WS와 REST 재생은 같은 행을 돌려준다.

### 7.2 기록과 전송

```go
type Emitter interface { // 트랜잭션 안에서 호출
    Emit(ctx context.Context, tx store.Tx, ev Event) (Envelope, error)
}
```

1. `UPDATE task SET event_seq = event_seq + 1 WHERE id=$1 RETURNING event_seq`: Task 행 락으로 seq가 단조 증가하고 빈틈이 없다.
2. `INSERT task_event(...)`: `ux_task_event_task_seq` 제약이 마지막 방어선이다.
3. 트랜잭션 헬퍼가 envelope을 "커밋 후 전송 목록"에 모은다. **커밋에 성공해야만** `Bus.Publish`를 호출한다.
4. `Bus`는 프로세스 내부 fan-out이다. 구독자는 WS hub와 Notifier(Discord 자리)다. 느린 구독자 때문에 실행이 막히지 않도록 구독자마다 버퍼 채널을 두고, 넘치면 그 구독자의 연결을 끊는다. 클라이언트는 `from_seq`로 다시 받아 간다.

### 7.3 WebSocket
프로토콜은 현행 `WsHandler`와 같다(`subscribe{task_id?, from_seq}` → 재생(500건 단위 배치) → `subscribed{replayed}` → 라이브, `ping/pong`, `unsubscribe`, `UNKNOWN_OP`). 재생 중에 도착한 라이브 이벤트와 seq가 겹치면 클라이언트가 걸러낸다(현행 방식 유지).

## 8. LLM

### 8.1 인터페이스

```go
type LLM interface {
    Chat(ctx context.Context, req ChatRequest) (ChatResponse, error)
}
type ChatRequest struct {
    System   string
    Messages []Message          // Role: user | assistant(ToolCalls) | tool(ToolCallID)
    Tools    []ToolSpec         // Name, Description, InputSchema json.RawMessage
    MaxTokens int
}
type ChatResponse struct {
    Text      string
    ToolCalls []ToolCall        // ID, Name, Args map[string]any
    Model     string
    Usage     Usage             // Input, Output, CacheRead, CacheWrite
}
```

### 8.2 어댑터와 레지스트리
- `"provider/model"` 문자열을 받아 `map[string]Factory`에서 어댑터를 만든다. 형식 오류는 현행과 같은 메시지로 400 `PIPELINE_INVALID`를 낸다.
- `anthropic/*`: `anthropic-sdk-go`. system prompt에 캐시 지정(`CacheControl`)을 붙인다. persona·conventions·knowledge가 길고, ReAct 루프 동안 반복해서 보내기 때문이다.
- `openai/*`: `openai-go`. 도구 인자가 JSON 문자열로 오므로 map으로 파싱한다.
- `ollama/*`: `openai-go` + `WithBaseURL`(Ollama의 OpenAI 호환 엔드포인트).
- `fake`: 현행 `FakeLLM`을 그대로 옮긴다. plan 텍스트, `write_file` 호출, 거부됐을 때 `fallback.md`로 재시도, `[[MODE:plan]]`·`[[COMMAND]]`·`[[FEEDBACK]]` 마커 해석까지 같다. `DEVSQUAD_FAKE_LLM=true`이면 모든 모델이 fake로 대체된다.
- API 키는 SDK 기본 환경 변수(`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`)에서만 읽는다. 코드와 로그에 남기지 않는다.

### 8.3 ReAct 루프
현행 `run_react`를 그대로 옮긴다. 도구 호출이 없는 턴이 나오면 끝내고, `max_iterations`에 도달하면 `agent.message`와 `hit_limit`을 남긴다. 도구 오류는 예외가 아니라 Observation 문자열(`[denied]`, `[not found]`, `[bad args]`)로 돌려준다.

### 8.4 토큰 예산 자리
각 `Chat` 호출 앞에 `BudgetGuard.Check(taskID)` 훅을 둔다. 1차 구현은 항상 통과시킨다. 강제 정책(초과 시 `run.paused{reason:"budget"}`)은 별도 범위다.

## 9. 도구, 샌드박스, 작업 디렉토리, 외부 연동 자리

- **tool_profile → 도구**: 현행 `registry.tools_for`의 표를 그대로 옮긴다(docs-writer, code-writer(+run_tests), reader, publisher).
- **Sandbox**: 현행 규칙을 유지한다.
  - 상대 경로만 허용하고, `..`와 절대 경로를 거부한다.
  - 시크릿 파일 패턴(`.env*`, `*.pem`, `*.key`, `*.p12`, `*.jks`, `id_rsa*`, `id_ed25519*`)과 보호 디렉토리(`secrets`, `.git`, `.ssh`, `.aws`, `node_modules`, `.venv`)를 막는다.
  - 읽기 200KB, 쓰기 2MB로 제한한다.
  - 추가로 `filepath.EvalSymlinks`를 거친 실제 경로가 workspace 안에 있는지 확인한다. 현행 `Path.resolve()`와 같은 효과다.
- **glob**: `doublestar` v4. 현행 `_glob_match`의 `**` 의미(0개 이상 디렉토리)와 맞는지 테스트 표로 고정한다.
- **run_tests**: `exec.CommandContext` + 프로세스 그룹 kill(`Setpgid`) + `WaitDelay`. 타임아웃은 600초다. 출력이 20,000자를 넘으면 앞뒤 10,000자만 남긴다.
  - 명령 분리는 현행 규칙을 따른다. `&&`가 없으면 `mvdan.cc/sh/v3/shell.Fields`로 나누고, 있으면 `bash -lc`로 실행한다.
- **workspace**: 현행 `WorkspaceManager.prepare`를 옮긴다. `local_path`를 복사할 때 IGNORE 목록을 쓰고, workspace root가 원본 안에 있으면 거부한다. 여기에 §6.8의 git 기준점이 추가된다.
- **외부 연동 자리** (이번 범위 밖): 아래 인터페이스만 정의하고 1차에서는 no-op 구현을 둔다.
  - `notify.Notifier`: Bus 구독자. Discord 승인 카드와 스레드 알림용.
  - `scm.Publisher`: publisher 내장 팀원의 PR 생성용.

## 10. 트랜잭션 정책 선언

공통 사항
- 트랜잭션 경계는 `app` 서비스 메서드와 orchestrator 커밋 함수에만 둔다(`store.WithTx`).
- 격리 수준은 READ COMMITTED(PostgreSQL 기본값)다.
- 커밋 후 처리(Bus 전송, Reconcile 호출, ctx 취소)는 `WithTx`가 모아 두었다가 **커밋에 성공했을 때만** 실행한다.
- 트랜잭션 안에서 LLM, HTTP, 파일, 서브프로세스를 호출하지 않는다.
- 이 서비스에는 AoN 강제 도메인(금전, 권한, 자격 증명, 테넌시)이 없다. 기본값인 All-or-Nothing을 따르고, 커밋 후 부수 효과만 Graceful로 둔다.

### U1. `TaskService.Create`

| 항목 | 내용 |
|---|---|
| 정책 | All-or-Nothing (DB) + 커밋 후 Reconcile |
| 트랜잭션 경계 | `TaskService.Create` 한 번 |
| 트랜잭션 전 준비 | workspace 준비, `pipeline.yaml`·팀원 로딩과 검증. 실패하면 400 응답을 주고 행은 만들지 않으며 workspace를 정리한다 |
| 상태 변경 | `task`(queued, pipeline 스냅샷, workspace) INSERT, `stage` × N(pending) INSERT |
| 비-DB 부작용 | workspace 디렉토리. 트랜잭션 전에 만들고, 트랜잭션이 실패하면 `defer`로 삭제한다. 프로세스가 죽어 남은 고아 디렉토리는 복구 루프가 Task 행이 없는 디렉토리를 찾아 정리한다 |
| 불변식 | Task당 stage_key 유일. 기존 `ux_stage_task_key` 제약이 강제 |
| 커밋 후 | `Reconcile`. 실패하거나 프로세스가 죽으면 Task가 queued로 남고 복구 루프가 이어간다 |
| 실패 응답 | 400 `PIPELINE_INVALID`, 400 `PROJECT_INVALID`(현행 AR 내부 코드를 공개 API로 올림, 15-API §7에 추가 필요), 404 project |

현행은 Task를 저장하는 트랜잭션과, AR을 호출한 뒤 Stage를 저장하는 트랜잭션이 나뉘어 있었다. 이제 외부 호출이 없으므로 한 트랜잭션으로 합친다.

### U2. `ApprovalService.Decide`

| 항목 | 내용 |
|---|---|
| 정책 | All-or-Nothing |
| 트랜잭션 경계 | `ApprovalService.Decide` 한 번 |
| 상태 변경 | `approval` 결정 UPDATE(`WHERE id=$1 AND status='pending' AND version=$2`, version+1) · `stage` 전이와 retry 카운터, `last_feedback`, (edit일 때) plan 또는 deliverable_summary 교체 · Task 상태 도출 · `approval.decided` 이벤트 · (반려 상한이면) `stage.blocked` 이벤트 |
| 불변식 | 승인은 한 번만 결정된다. 조건부 UPDATE가 0행이면 409 `APPROVAL_ALREADY_DECIDED`. Stage당 대기 승인은 최대 1건이며 `ux_approval_stage_pending`이 강제 |
| 동시성 | 웹과 Discord에서 동시에 결정해도 version 조건 때문에 한쪽만 성공하고 나머지는 409. 현행 `@Version` 동작과 같다 |
| 입력 검증 | reject는 feedback 필수(400 `FEEDBACK_REQUIRED`), edit은 edited_content 필수. 트랜잭션 전에 검증 |
| 커밋 후 | `Reconcile`(Graceful). 실패해도 결정은 이미 DB에 있으므로 복구 루프가 이어간다. 그래서 `resume_pending`이 필요 없다 |

**유효성:**
- A1: 상태 변경이 한 트랜잭션 안에 있다.
- A2: 외부 호출이 없다.
- A3: 오류가 나면 반환과 함께 롤백한다(`WithTx`가 error면 Rollback).
- A4: 커밋 후 처리가 트랜잭션을 새로 열지 않는다.
- A5: 409, 400, 404를 구분해 응답한다.

### U3. 단계 claim과 결과 커밋 (`commitPlan`, `commitExecute`)

| 항목 | 내용 |
|---|---|
| 정책 | All-or-Nothing (커밋 함수마다) |
| 상태 변경 | §6.4 표 참조 |
| 불변식 | 한 단계의 결과는 한 번만 반영된다. `attempt`·`status` 조건부 UPDATE(펜싱)와 `ux_approval_stage_kind_retry`가 강제 |
| 비-DB 부작용 | LLM 호출과 파일 쓰기는 **커밋 전, 트랜잭션 밖**에서 한다. 커밋이 0행이면 결과를 버리고, 파일은 다음 execute 시작 시 §6.8 롤백으로 되돌린다 |
| 실패 처리 | 커밋 함수 안의 오류는 롤백 후 §6.7 실패 정책(Task failed)으로 처리한다 |

### U4. `TaskService.Pause` / `Resume` / `Cancel`

| 항목 | 내용 |
|---|---|
| 정책 | All-or-Nothing (Task 전이 + 이벤트) |
| 동시성 | `task.version` 조건부 UPDATE. 충돌하거나 허용되지 않는 전이면 409 `INVALID_TRANSITION` |
| 커밋 후 | Resume은 Reconcile, Cancel은 ctx 취소(Graceful, 프로세스 내부라 실패 경로가 사실상 없음) |

### U5. `Emitter.Emit` (진행 이벤트, usage)

| 항목 | 내용 |
|---|---|
| 정책 | All-or-Nothing (seq 발급 + task_event INSERT + (usage면) usage_record INSERT) |
| core / aux | core: DB 기록. aux: Bus 전송(WS, Notifier) |
| 복구 경로 | WS로 못 보낸 이벤트는 클라이언트가 `from_seq`로 다시 받아 간다(G4). Notifier 실패는 `slog.Error`와 메트릭으로 남긴다 |
| 알려진 한계 | execute 단계 중간에 프로세스가 죽으면 그때까지의 usage는 이미 기록되어 있고, 다시 실행하면 또 기록된다. 실제로 일어난 호출이므로 과금 관점에서는 맞는 값이다 |

## 14. 테스트 전략

| 층 | 대상 | 방식 |
|---|---|---|
| 단위 | `domain` 상태 기계 | 현행 `TaskStateMachineTest`, `StageStateMachineTest`, `ApprovalDomainTest` 케이스를 표 기반 테스트로 이식 |
| 단위 | `pipeline` | 현행 `test_pipeline.py`의 DAG·사이클·중복·levels 케이스 이식 |
| 단위 | `tools` Sandbox | 현행 `test_sandbox.py` 이식 + symlink 탈출 + doublestar `**` 의미 표 |
| 단위 | `llm` 어댑터 | httptest 서버에 녹화한 응답을 재생. OpenAI 인자 문자열 파싱, Anthropic content block 처리 |
| 통합 | `app` + `store` | testcontainers-go Postgres. 낙관적 락 409, 제약 위반, 커밋 후 hook이 롤백 시에는 실행되지 않는지 |
| 통합 | orchestrator 전체 흐름 | FakeLLM + Postgres. 현행 `test_stage_gates.py`·`test_builder.py`·`test_api_runs.py` 시나리오(승인, 반려 재시도, 상한 blocked, edit, 게이트 없는 Stage, 병렬 FE∥BE) |
| 장애 | 재시작 복구 | execute 도중 ctx를 취소해 크래시를 흉내 내고, 새 Orchestrator로 Reconcile한 뒤 결과물이 한 번만 반영되는지, workspace의 write_paths가 롤백되는지 |
| 동시성 | 동시 결정 | goroutine 2개가 같은 approval에 Decide를 호출하면 하나만 성공하고 하나는 409 |
| 동시성 | 중복 Reconcile | 같은 Task에 Reconcile을 동시에 N번 호출해도 단계 goroutine이 하나만 뜨는지(펜싱) |
| 시간 | 복구 루프 | `testing/synctest`로 fixed-delay를 결정적으로 검증 |

- 롤백을 검증하는 테스트는 테스트 자체를 트랜잭션으로 감싸지 않는다(감싸면 검증이 무효가 됨).
- 테스트 시간은 주입한 `func() time.Time`이나 synctest로 제어한다. 저장하는 시각은 모두 UTC `time.Time`이다.

## 15. 미결 사항

| # | 질문 | 영향 | 제안 |
|---|---|---|---|

| Q3 | `failed` Task를 재시도할 수 있게 하는가 | 상태 기계 확장(`failed → running`) | 1차는 현행대로 터미널 |
| Q4 | 기존 Flyway DB가 있는가 | baseline 마킹 절차 | Phase 0~1이라 없다고 가정하고 초기화 |
| Q5 | Stage 실행 순서: 선행 Stage만 기다림(D5) vs 레벨 전체를 기다림(BSP) | 실행 순서, UI 표시 | D5 채택. 다만 UI가 레벨 단위 진행을 전제로 한다면 확인 필요 |
| Q6 | 내장 publisher 팀원(PR 생성) | `scm.Publisher` 구현 시점 | 현행처럼 문서형 no-op 팀원으로 유지 |
