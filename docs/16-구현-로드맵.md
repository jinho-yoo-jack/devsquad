# 구현 로드맵 — Phase 1~3 작업 분해

> [!tip] 핵심 Takeaway
> Phase 1의 목표는 기능이 아니라 **"끝까지 도는 뼈대"** 다. 기획 agent 하나로 명령 → Plan → 승인 → 실행 → Deliverable → 승인 → 완료가 웹 UI에서 돌고, 승인 대기 중에 두 서버를 재시작해도 이어지면 Phase 1은 끝이다. 그 뼈대 위에 Phase 2에서 팀원과 Discord를, Phase 3에서 GitHub와 검수를 얹는다. 각 Phase의 완료 기준(Definition of Done)을 먼저 정하고 그것만 만든다.

## 0. 저장소 구성과 공통 준비

모노레포 하나로 시작한다.

```
devsquad/
├── control-plane/     # Spring Boot
├── agent-runtime/     # Python
├── web/               # Next.js
├── infra/             # docker-compose.yml, .env.example, Flyway는 CP 안
├── docs/              # 이 기획 문서들 (또는 링크)
└── examples/
    └── sample-project/.devsquad/   # 데모용 컨텍스트 파일 세트
```

공통 준비 작업: docker-compose(postgres, redis) · GitHub Actions(CP gradle test, AR pytest, web vitest, openapi 타입 생성 검증) · 커밋 컨벤션. `.devsquad/` 템플릿은 `examples/devsquad-templates/`에 이미 작성되어 있다(17-Agent-정의-가이드). 데모 대상 repo는 사용자의 개인 샘플 프로젝트(Spring + Next.js 소규모)를 권장한다.

## 1. Phase 1 — 뼈대 (기획 agent + 승인 게이트 + 웹 관찰)

### 완료 기준 (DoD)

1. 웹 `/tasks/new`에서 명령을 넣으면 Task가 생성되고 상세 화면에서 타임라인이 실시간으로 흐른다.
2. planner의 Plan이 승인 패널에 뜨고 approve / reject(피드백) / edit 세 경로가 모두 동작한다. reject 시 재제출 버전이 v2로 올라온다.
3. 승인 후 planner가 `docs/spec/*.md`를 작성(workspace 내)하고 Deliverable이 산출물 뷰어에 렌더된다.
4. Deliverable 승인 시 Task가 `completed`가 된다.
5. Plan 승인 대기 상태에서 `docker compose restart control-plane agent-runtime` 후 승인하면 그대로 이어진다.
6. 반려 3회 초과 시 `blocked` 상태와 알림이 표시된다.
7. Playwright E2E 1개(위 1~4 경로, fake LLM 모드)가 CI에서 통과한다.

## 2. Phase 2 — 팀 (4 agent + 병렬 + Discord)

### 완료 기준

1. Discord `/task`로 만든 Task가 기획 → 디자인 → FE ∥ BE 네 Stage를 Discord 카드 승인만으로 통과한다.
2. FE·BE Stage가 동시에 `executing`이며 웹 파이프라인 바에 병렬로 그려진다.
3. 웹에서 승인한 Approval의 Discord 카드가 1초 내 "승인됨(웹)"으로 바뀌고, 반대도 성립한다.
4. Agent 설정 화면에서 planner `conventions.md`를 수정 → 저장(GitHub 커밋) → 다음 Task의 Plan에 반영된다.
5. 승인 버튼 연타·웹 동시 클릭에도 결정이 한 번만 적용된다.

### 작업 분해

- AR: designer/frontend/backend persona·conventions 템플릿, 역할별 도구 화이트리스트(git.commit, test_runner 포함, push 제외), `merge_by_key` 병렬 검증, System Prompt 토큰 예산 관리(knowledge 요약), `agent.thinking` 요약 품질 조정, workspace를 git clone 기반으로 전환(installation token).
- CP: JDA 어댑터(Gateway, slash, defer, thread 생성, 카드 렌더, 버튼·Modal, 결정 동기화 리스너), GitHub App 인증 + 파일 읽기/쓰기(Agent 설정 저장), `pipeline.yaml`을 repo에서 읽어 Stage 생성, 요약 WS 채널, 헤더 승인 목록 API.
- Web: 4 AgentCard, 병렬 `PipelineBar` 레이아웃(`layoutStages` 테스트), 산출물 Stage 탭, Agent 설정 화면(CodeMirror + diff 미리보기), 헤더 승인 드롭다운, 모바일 탭 레이아웃, Discord thread 링크.
- 공통: Discord 봇 등록·권한, GitHub App 생성·설치, 데모 repo에 `examples/devsquad-templates/.devsquad/` 전체 세트 커밋.
- 사용자 정의 팀원(FR-25~27): AR `agents/loader`가 임의 폴더명·`tool_profile`·`write_paths`를 읽어 도구를 바인딩, `pipeline.yaml` 검증에 폴더 존재·프로필 유효·쓰기 경로 충돌 검사 추가, `devsquad:*` YAML 블록 파서(summary/openapi/api-usage/review). CP `POST /projects/{id}/bootstrap`에 템플릿 선택 파라미터, 템플릿 라이브러리를 CP 리소스로 번들. Web 팀원 설정 화면의 템플릿 갤러리·검증 배지.

## 3. Phase 3 — 결과물 (GitHub PR + 상호 검수 + 예산)

### 완료 기준

1. FE·BE Deliverable 승인 시 `devsquad/<task-id>/<role>` 브랜치가 원격에 push된다.
2. reviewer가 FE 코드의 API 호출과 BE `docs/api/*.md`를 대조해 불일치 목록을 Deliverable로 내고, 의도적으로 심은 불일치 1건을 잡는다.
3. review 승인 시 PR 2개(또는 1개 통합)가 생성되고 본문에 spec 링크·승인 이력이 포함되며 Discord thread에 링크가 올라온다.
4. PR에 리뷰 코멘트를 달면 Discord·웹에 알림이 뜬다.
5. 토큰 예산 초과 시 Task가 `paused`되고 예산 증액 후 resume된다.
6. `RunRecoveryJob`이 AR 강제 종료 후 `execute` 중이던 Stage를 재실행해 완료시킨다.

### 작업 분해

- AR: `commit_result`의 push(승인 후 부작용), `review` 노드(API 호출 추출·대조 프롬프트 + 구조화 출력), `publish` 노드(멱등 PR 요청), `execute` 시작 시 `git checkout .` 결정성, 테스트 러너 컨테이너 격리, review 반려 시 부모 그래프 `Command(goto="frontend")` 재진입.
- CP: `POST /internal/prs`, PR 본문 렌더러, GitHub webhook(HMAC, review comment → 알림), usage 예산 검사 → cancel/pause, 예산 증액 API, WS 다중 인스턴스 Pub/Sub, 운영 대시보드용 메트릭(Micrometer).
- Web: `DiffView`(unified/split), PR 링크·리뷰 코멘트 표시, 토큰 예산 UI(증액 다이얼로그), `pipeline.yaml` 시각 편집(선택).

## 4. 리스크와 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| `interrupt()` 재개 시 노드 재실행으로 LLM 재호출·비용 중복 | 비용, 지연 | gate 노드에 LLM 두지 않음(설계 반영). `execute`는 checkpoint 경계를 좁히기 위해 필요 시 서브 노드 분리 |
| Discord 3초 응답 제한 | 인터랙션 실패 | 모든 핸들러 `deferReply` 우선, 처리 비동기 |
| FE·BE 병렬 시 같은 파일 수정 충돌 | 코드 산출물 손상 | 역할별 쓰기 경로 화이트리스트(`web/**` vs `server/**`), 공유 파일(`docs/api`)은 BE만 쓰기 |
| agent가 conventions를 무시 | 품질 | Deliverable gate 전에 결정적 검사(lint, 경로 규칙) 노드 추가 — Phase 2 후보 |
| 토큰 폭주 | 비용 | `execute_max_iterations`, Task 예산, usage 이벤트 실시간 집계 |
| Python·Java 두 스택 유지 부담 | 속도 | 내부 계약을 이 문서 §15로 고정, 각 스택은 계약 테스트로 독립 검증 |
| LLM 벤더 종속 | 교체 비용 | LangChain 모델 추상화, `pipeline.yaml`의 `model` 필드로 Stage별 교체 |

## 5. 결정 대기 항목

- 디자인 agent 산출물에 HTML 목업 포함 여부 (제안: Phase 2는 Markdown + 컴포넌트 트리 JSON, 목업은 Phase 3 이후).
- edit 승인 후 agent 재정리 여부 (제안: 사람이 수정한 원문 그대로 다음 Stage로).
- review 불일치 시 수정 주체 (제안: BE 계약 기준, FE Stage 재진입).
- PR 단위: FE/BE 각 1개 vs 통합 1개 (제안: 저장소 구조에 따라 `pipeline.yaml` `pr.mode`로 선택).
- 데모 대상 저장소 선정.
